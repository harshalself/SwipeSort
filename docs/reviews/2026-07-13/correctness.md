# Correctness & Bugs
**Reviewer:** correctness-lens  **Date:** 2026-07-13  **Verify status:** pass

## Summary

The most dangerous cluster is in `SwipeSessionModel` and `SwipeStackView`: move operations execute immediately against the real photo library via `swipeUp(intoAlbumId:)` but are also enqueued for commit — creating double-execution on commit. A paired bug makes `commitDecisions()` silently ignore all `.moveToAlbum` decisions after the `.delete` step, so that path exits early even when only moves are pending. The undo walk contains a silent `target = 0` fallback that navigates to the wrong photo when the popped identifier is not found. `PhotoKitLibrary` is `@unchecked Sendable` with unsynchronised mutable state (`fetchResult`, `fetchedAuth`, `activeFilter`) that can be concurrently mutated from multiple async call sites. Several secondary findings cover dry-run coverage gaps, cancellation ordering, a stale-index hazard in `DecisionQueue.removeCommitted`, and fragile auth-state handling.

## Findings

### F1 — `swipeUp` double-executes album move: once immediately, once at commit [SEVERITY: high]
- **File:** SwipeSort/Features/Swipe/SwipeSessionModel.swift:98
- **What:** `swipeUp(intoAlbumId:)` calls `library.moveAssets(...)` directly, then also records a `.moveToAlbum` decision in the queue; if the caller later invokes `commitDecisions()` the move is never re-executed (see F2), but the decision remains in the queue and counts against `movedToAlbumCount`, misleading the summary. More critically, any code path that does attempt to re-commit moves (e.g., a future refactor of `commitDecisions` to handle moves) will issue the operation twice, moving the asset a second time or silently failing.
- **Why it matters / failure scenario:** User swipes an asset into Album A. The asset is immediately moved (correct). The decision is also stored. If the commit path is later extended to flush `.moveToAlbum` decisions (the natural next step), the asset is moved again — either into a duplicate album membership or triggering an error that surfaces as "Failed" to the user. Even today the summary shows an inflated `movedToAlbumCount` on `finishedSummary` after a delete commit because `removeCommitted()` only strips `.delete` decisions, leaving stale moves in the queue permanently.
- **Suggested fix direction:** Decide on one of two clean contracts: (a) moves are truly fire-and-forget (remove the `.moveToAlbum` case from `DecisionQueue` entirely and track counts separately), or (b) moves are deferred like deletions (remove the immediate `library.moveAssets` call from `swipeUp` and commit them in `commitDecisions`). Option (a) matches the current plan notes ("album moves happen instantly") and is the simpler fix.
- **Verified:** yes (adversarial subagent confirmed — severity revised critical → high because `commitDecisions` doesn't re-execute moves today, so the data-loss narrative doesn't fire in current build; structural double-execution hazard + stale-queue summary inflation remain)

### F2 — `commitDecisions()` exits early when no deletions exist, skipping any unflushed move decisions [SEVERITY: high]
- **File:** SwipeSort/Features/Swipe/SwipeSessionModel.swift:239
- **What:** `commitDecisions()` returns `.success(affectedCount: 0)` and sets `phase = .finished` immediately when `pendingDeletions` is empty, without processing any `.moveToAlbum` entries that might be in the queue.
- **Why it matters / failure scenario:** If the user only performs album-move swipes (no deletions) and then taps "Delete All" in `DeletionQueueView` or reaches the auto-commit path, `commitDecisions()` returns `success(0)` and sets `phase = .finished` without executing any moves. Under the current code, moves already fired immediately (F1), so no data loss occurs today — but the control flow is wrong: `phase` transitions to `.finished` unconditionally, which triggers the auto-present-queue or auto-commit path in `finishedSummary.task` even for sessions that had zero deletions. The guard is also the only protection if F1 is fixed (moves become deferred); at that point this early exit would silently drop all pending moves.
- **Suggested fix direction:** Separate the "nothing to commit at all" check from the "no deletions" check. Evaluate both deletion and move queues independently before deciding to exit early.
- **Verified:** yes (adversarial subagent confirmed — severity revised critical → high; move-only sessions incorrectly transition to `.finished`, triggering auto-commit paths, though no move data is lost today since moves fire immediately in `swipeUp`)

### F3 — `PhotoKitLibrary` is `@unchecked Sendable` with unsynchronised mutable state [SEVERITY: high]
- **File:** SwipeSort/Core/PhotoKitLibrary.swift:18
- **What:** `fetchResult`, `fetchedAuth`, and `activeFilter` are mutable instance variables on a class marked `@unchecked Sendable` with no lock or actor isolation; concurrent async callers can read and write these without coordination.
- **Why it matters / failure scenario:** `SwipeSessionModel.loadCurrent()` fires four concurrent async tasks (`async let currentThumbTask`, `async let currentKindTask`, etc.) that all call into the library. If any two of these — or a background `refreshFetchResult()` triggered by `PhotoLibraryChangePublisher` while `loadCurrent()` is running — race on `fetchResult`, one of the following can occur: (1) a nil `fetchResult` is observed mid-update and a fresh fetch fires concurrently; (2) `fetchedAuth` is written after the guard in `ensureFetchResult()` but before the new fetch completes, causing the stale empty result to be re-cached. On a 50 k-asset library this can produce an incorrect `totalCount = 0` or stale identifiers silently.
- **Suggested fix direction:** Make `PhotoKitLibrary` an `actor` (preferred) or add a serial `DispatchQueue` protecting reads/writes to `fetchResult`, `fetchedAuth`, and `activeFilter`. Remove `@unchecked Sendable`; let the actor's `Sendable` conformance flow naturally.
- **Verified:** plausible — structural race is present in the code (`@unchecked Sendable` with three unguarded `var` properties + `refreshFetchResult` writing `fetchResult = nil` from a NotificationCenter callback), but proving an active race fires requires runtime observation. Severity held at high; latent Swift 6 concurrency hazard is real.

### F4 — `undo()` silently navigates to index 0 when the undone asset is not found in the fetch result [SEVERITY: high]
- **File:** SwipeSort/Features/Swipe/SwipeSessionModel.swift:182
- **What:** When the backward scan in `undo()` fails to locate the popped identifier (asset deleted externally, filter changed, or stale `localIdentifier`), `target` stays at its initialised value of `0`, so `currentIndex` jumps to the very first photo in the library rather than aborting or emitting a recoverable error.
- **Why it matters / failure scenario:** User swipes photo #4000, then the Photos library changes externally (iCloud sync deletes that asset) while the queue is still open. User taps Undo. The `while` loop exits without finding the asset, `target` is `0`, and the swipe view jumps to photo #1 — a completely wrong position. Because `phase` is also set to `.ready` and `loadCurrent()` is called, the user is now swiping photos they already reviewed.
- **Suggested fix direction:** Initialise `target` to `nil` (or use an `Optional<Int>` accumulator). After the loop, if `target` is still `nil`, restore `currentIndex` to `max(0, currentIndex - 1)` as a best-effort fallback and surface an in-session warning rather than silently jumping to index 0.
- **Verified:** yes (adversarial subagent confirmed — `var target = 0` at line 182, no `Optional` wrapping, no not-found guard)

### F5 — Race condition: `DragGesture.onEnded` dispatches a `Task` that mutates `dragOffset` from the new task's continuation, racing with any concurrent gesture [SEVERITY: medium]
- **File:** SwipeSort/Features/Swipe/SwipeStackView.swift:607
- **What:** Each gesture terminal branch (up/down/left/right threshold) fires `Task { await model.swipe(...); dragOffset = .zero }`. `dragOffset` is a `@State` var, so setting it is safe, but the `await model.swipe(...)` call suspends the task, allowing a second gesture to start before `dragOffset = .zero` executes.
- **Why it matters / failure scenario:** Rapid swipes: user flicks right, `Task` for `.right` is dispatched and suspended in `model.swipe`. Before it resumes, user flicks up — another `Task` for `.up` is dispatched. Both tasks resume roughly simultaneously. The first task sets `dragOffset = .zero` after the second gesture's animation has already started, clobbering the second animation mid-flight. More critically, both `model.swipe` calls run concurrently — `@MainActor` serialises them on the main actor's serial queue, but the queue can still have two pending swipe-advance calls, resulting in double-advance (skipping an asset) if both advance before the first has updated `currentIndex` and before the second reads it. `currentIndex` is only written in `advance()` and read in `loadCurrent()`, both of which are `@MainActor`, so within a single run-to-completion they are safe — but two enqueued tasks that both call `advance()` before checking `totalCount` can advance past the end.
- **Suggested fix direction:** Introduce an `isProcessingSwipe: Bool` flag (or a `@MainActor`-isolated actor flag); set it at gesture-end before dispatching the Task, clear it in the Task's `finally` path. Ignore further gesture completions while a swipe is in flight.
- **Verified:** plausible — severity revised high → medium. `@MainActor` serialisation on `SwipeSessionModel` refutes the double-`advance()` scenario; the mid-animation `dragOffset` clobber (second gesture animation overwritten by first Task's post-await reset) remains plausible but unproven without running the app.

### F6 — `commitDecisions()` sets `phase = .finished` before the system delete prompt is answered when user cancels [SEVERITY: high]
- **File:** SwipeSort/Features/Swipe/SwipeSessionModel.swift:246
- **What:** `phase = .committing` is set before `library.commitDeletions` is awaited. If the user cancels the iOS system alert, `phase = .finished` is still set (line 247), and `queue.removeCommitted()` is only called on `.success`, so the queue is correctly preserved — but `phase` is permanently `.finished` even though there are still pending deletions.
- **Why it matters / failure scenario:** User has 10 photos queued for deletion, taps "Delete All", then cancels the iOS system alert. `CommitResult.cancelledByUser` is returned, the queue is preserved (correct), but `phase` is now `.finished`. The `finishedSummary` view renders and its `.task` fires the auto-present-queue / auto-commit path again (`didAutoPresentQueue` and `didAutoCommit` are already `true`), so the user cannot see a re-try path without restarting the session. The deletions remain pending in the queue but the UI is stuck on the finished screen.
- **Suggested fix direction:** Only transition `phase` to `.finished` on `.success`. On `.cancelledByUser` or `.failed`, return `phase` to `.ready` so the user can retry. The `finishedSummary` guard `commitResult == nil` already handles the "not yet committed" visual, but `phase` must revert to allow the deck to become interactive again.
- **Verified:** yes (adversarial subagent confirmed — `phase = .finished` at line 247 is unconditional; on `.cancelledByUser` the queue is preserved but the UI is stuck on the finished screen)

### F7 — `swipeFavorite` / `swipeKeep` aliases set `isFavorite = true` unconditionally; no way to un-favourite during a session [SEVERITY: medium]
- **File:** SwipeSort/Features/Swipe/SwipeSessionModel.swift:77
- **What:** `swipeKeep()` calls `swipeFavorite()` which always calls `library.setFavorite(..., isFavorite: true)` — there is no corresponding path that sets `isFavorite: false`, and `toggleFavorite()` is not wired to any gesture in `swipe(_:using:)`.
- **Why it matters / failure scenario:** The naming implies "keep" (do not delete, no favourites side-effect) but the implementation silently marks every "kept" photo as a Photos favourite. On a 50 k-asset library where the user swipes "keep" on thousands of photos, all of those become favourites — a destructive change to the library that the user did not request. `toggleFavorite(_:)` exists but is only callable if wired up externally; there is no call site in `SwipeStackView`.
- **Suggested fix direction:** Separate the `.keep` semantic from the favouriting semantic. `swipeKeep()` should only record a `.keep` decision with no side effects. Create a dedicated `swipeFavourite()` path (or a separate button) that explicitly sets `isFavorite = true`. The gesture mapping in `swipe(_:using:)` currently maps "down" / "left" (depending on mode) to "FAVORITE" per the drag-hint labels — that is the correct UX. Remove the side effect from the keep path.
- **Verified:** plausible — severity revised high → medium. `swipeKeep()` aliases `swipeFavorite()` correctly, but the current gesture-routing code in `swipe(_:using:)` (lines 146-163) calls `swipeFavorite()` directly and never `swipeKeep()`. Live impact is limited to direct API misuse; the misleading alias is still a real bug waiting to bite.

### F8 — `DecisionQueue.removeCommitted()` only strips `.delete`; stale `.moveToAlbum` decisions accumulate indefinitely [SEVERITY: high]
- **File:** SwipeSort/Core/SwipeDecision.swift:70
- **What:** After a successful commit, `removeCommitted()` deletes only `.delete` decisions. `.moveToAlbum` entries are never removed from `decisions`, causing `movedToAlbumCount` and `pendingDeletions` computations to grow unboundedly across repeated commit calls in a long session.
- **Why it matters / failure scenario:** User runs a 500-photo session; swipes 200 into albums (immediately executed) and 300 to delete. After commit, the 300 `.delete` entries are stripped but the 200 `.moveToAlbum` entries remain. If the user starts a new batch (add more photos to delete) and commits again, `movedToAlbumCount` still shows 200 from the previous batch on the summary screen, giving a false "Moved to Album: 200" count. More importantly, if F1 is fixed and moves are deferred, a second `commitDecisions()` call would re-execute all 200 stale moves.
- **Suggested fix direction:** Add a `removeAll(matching:)` variant that strips both `.delete` and `.moveToAlbum` decisions, or add a separate `removeMoveDecisions()` call that `commitDecisions()` invokes after moves are successfully processed.
- **Verified:** yes (adversarial subagent confirmed — `removeCommitted()` at lines 70-75 only strips `.delete`; `.moveToAlbum` entries accumulate indefinitely, inflating `movedToAlbumCount` across commits)

### F9 — `PhotoLibraryChangePublisher.register()` is called from `PhotoKitLibrary.init()`, which runs before authorization is granted [SEVERITY: high]
- **File:** SwipeSort/Core/PhotoKitLibrary.swift:28
- **What:** `PhotoLibraryChangePublisher.shared.register()` calls `PHPhotoLibrary.shared().register(self)` inside `init()`, which executes before the user has granted library access.
- **Why it matters / failure scenario:** On first launch, `MainTabView` creates a `PhotoKitLibrary` instance before authorization is requested. Registering a `PHPhotoLibraryChangeObserver` without authorization is documented by Apple to silently no-op or log a privacy warning, but more importantly, if authorization is later denied or restricted the observer remains registered and will fire on any library change, triggering `loadAssets()` / `loadAlbums()` calls in views that have no valid fetch cursor. Each of those calls reaches `ensureFetchResult()`, which re-evaluates auth — the guard at line 448 (`authIsUsable`) would prevent caching, but every view re-indexing on every library change (even during an unrelated iCloud sync) when the user is not authorised adds unnecessary work.
- **Suggested fix direction:** Move `register()` to the `requestAuthorization()` success path in `PhotoKitLibrary`, called only after `.authorized` or `.limited` is confirmed. The same call site in `start()` within `SwipeSessionModel` makes this easy to wire.
- **Verified:** yes (adversarial subagent confirmed — `init` at lines 26-28 unconditionally calls `PhotoLibraryChangePublisher.shared.register()`; docstring at line 22 even says "Call once after photo-library access is granted", a documented intent violation)

### F10 — `undo()` for `.moveToAlbum` with `fromAlbumId == nil` calls `removeAssetsFromAlbum` even if the original add failed silently [SEVERITY: medium]
- **File:** SwipeSort/Features/Swipe/SwipeSessionModel.swift:173
- **What:** When `fromAlbumId` is `nil` (swiping from All Photos), undo calls `library.removeAssetsFromAlbum([id], albumId: toAlbumId)`. The return value is discarded (`_ = await ...`). If the original move returned an error (e.g., the destination album was read-only and the real `moveAssets` silently failed despite returning `.success` due to a dry-run bypass), the undo will attempt to remove an asset that was never added, which either no-ops or errors.
- **Why it matters / failure scenario:** Dry-run mode returns `.success` without actually moving (correct), but the decision is still enqueued. Undo then calls `removeAssetsFromAlbum` with the real library — which with dry-run OFF would attempt to remove the asset even though it was never added. The result is a spurious "remove from album" operation that does nothing (if the asset isn't in the album) but could be logged as an error or, in edge cases, could remove a legitimately placed asset if the album has an asset with the same identifier from an earlier non-dry-run session.
- **Suggested fix direction:** Check the result of `removeAssetsFromAlbum` in `undo()` and surface failures. Also: do not record `.moveToAlbum` decisions in dry-run mode — log the intent but skip the `queue.record()` call, or clear the entry if the underlying `moveAssets` returns `.failed`.
- **Verified:** pending

### F11 — `BulkDeleteView.task(id: filter)` calls `library.applyFilter(filter)` on the shared library, mutating shared state for other views [SEVERITY: medium]
- **File:** SwipeSort/Features/Landing/BulkDeleteView.swift:100
- **What:** `BulkDeleteView` calls `library.applyFilter(filter)` on the same `PhotoLibraryProviding` instance passed from the app root. This mutates the `activeFilter` and clears `fetchResult` on the shared library, affecting any concurrent `RecentsView` or `AlbumsView` that hold a reference to the same instance.
- **Why it matters / failure scenario:** User opens `BulkDeleteView` from one tab while `RecentsView` is mid-load on another tab. `applyFilter` clears the fetch cursor. `RecentsView.loadAssets()` calls `library.refreshFetchResult()` then `library.assetCount()`, but the count now reflects `BulkDeleteView`'s filter (e.g., "Videos only") rather than the Recents filter, producing an incorrect asset list for the Recents grid.
- **Suggested fix direction:** `BulkDeleteView` should operate on a private library scope — either by calling `library.scoped(toAlbumId:)` (though that's album-scoping, not filter-scoping) or, better, by wrapping the library in a filter-aware wrapper that applies its filter locally without touching the shared instance's state. Alternatively, instantiate a new `PhotoKitLibrary()` for the bulk-delete context.
- **Verified:** pending

### F12 — `livePhoto(for:targetSize:)` never resumes continuation for the degraded-delivery first callback when a final non-degraded result never arrives [SEVERITY: medium]
- **File:** SwipeSort/Core/PhotoKitLibrary.swift:388
- **What:** The `requestLivePhoto` callback only resumes when `live != nil`, or when `hasError || cancelled || !isDegraded`. If the first callback delivers a degraded live photo (`live != nil`, `isDegraded == true`), the continuation resumes correctly. But if the first callback delivers `live == nil` AND `isDegraded == true` (still waiting on network), and then the network times out without ever calling the callback again, the continuation hangs forever.
- **Why it matters / failure scenario:** For an iCloud-only Live Photo on a slow connection: PhotoKit sends `live = nil, isDegraded = true` (download in progress), then the connection drops without sending a final callback. The `async` call to `library.livePhoto(for:)` in `LivePhotoCardView` never returns, the card never renders, and the associated `Task` is never completed — leaking the task until the session is torn down.
- **Suggested fix direction:** Add a `PHImageRequestID` cancellation token and cancel it on task cancellation (via `withTaskCancellationHandler`). Also add a timeout path that resolves `nil` after a reasonable interval, matching the approach used for `thumbnail(for:)` which has similar exposure but is less likely to hang because `deliveryMode = .highQualityFormat` gives a definitive terminal callback.
- **Verified:** pending

### F13 — `RecentsView.loadAssets()` cap of 500 assets creates an inconsistent index space with the swipe session [SEVERITY: medium]
- **File:** SwipeSort/Features/Landing/RecentsView.swift:252
- **What:** `loadAssets()` fetches at most 500 identifiers (`limit = min(count, 500)`), but `SwipeStackView` is initialised with `initialIndex` derived from the grid's local array position (0–499), while the underlying `PHFetchResult` in the library contains all `count` assets (potentially 50,000+). When the user taps photo at grid index 300, `SwipeSessionModel` is told `initialIndex: 300`, but if the session was opened via `initialAssetId` the correct asset is found. However, if `initialAssetId` is stale (asset deleted between grid load and swipe start), `currentIndex = min(initialIndex, max(0, totalCount - 1))` falls back to `initialIndex = 300`, which is correct in the local-500 space but coincidentally correct in the full library space only if the fetch order matches.
- **Why it matters / failure scenario:** Recents fetches newest-first; the swipe session uses the same sort. Grid index 300 = 300th newest photo. `SwipeSessionModel` initialises to `currentIndex = 300` in a library of potentially 50,000+ assets — which happens to be correct because the same sort order is used. However, if the user has a filter applied that restricts the grid to fewer assets, the index-space mismatch becomes real: the grid shows filtered index 50, but the swipe session starts at unfiltered library index 50. The `initialAssetId` path rescues this, but only if the asset still exists.
- **Suggested fix direction:** Always pass `initialAssetId` when launching from a grid tap (already done at line 133), and rely solely on the identifier lookup in `loadInitial()`. Remove the `initialIndex` fallback or document clearly that it is unreliable for filtered sessions. Consider removing the 500-asset cap entirely and relying on `LazyVGrid` + `WindowedThumbnailCache` for memory management.
- **Verified:** pending

### F14 — `AlbumGridView.getScopedLibrary()` stores result in `@State` but is called in `body` — may create multiple instances before state settles [SEVERITY: medium]
- **File:** SwipeSort/Features/Landing/AlbumsView.swift:308
- **What:** `getScopedLibrary()` checks `scopedLibrary` for nil and initialises it if absent, storing the result back into `@State`. However, `body` is a computed property that can be called multiple times on the main thread in a single render cycle (e.g., during the reconcile phase). Each call to `getScopedLibrary()` in the `ForEach` cell closures (lines 170, 271, 277) may see `scopedLibrary == nil` on the first render, create a new instance, and try to assign it — with @State's `wrappedValue` setter being synchronous it should remain consistent, but the multiple construction calls in one render do wasteful work.
- **Why it matters / failure scenario:** Each call to `PhotoKitLibrary(albumId:)` inside `getScopedLibrary()` registers a new `PHPhotoLibraryChangeObserver` via `PhotoLibraryChangePublisher.shared.register()`, which calls `PHPhotoLibrary.shared().register(self)`. If `getScopedLibrary()` is called three times in a render before `@State` propagates the first assignment, three `PhotoKitLibrary` instances are constructed, each registering as observers. The singleton `PhotoLibraryChangePublisher.shared` is registered three times with the system, so `photoLibraryDidChange` fires once but `NotificationCenter` posts once — that part is fine. But three `PhotoKitLibrary` instances exist, each with their own `PHCachingImageManager`, which is a significant resource each.
- **Suggested fix direction:** Compute `scopedLibrary` lazily in `.task` or `onAppear`, not inline in `body`. Alternatively, initialise it in `init()` if `album.id` is known at that point.
- **Verified:** pending

### F15 — `WindowedThumbnailCache.slide()` does not guard against concurrent calls overlapping on `currentWindow` [SEVERITY: medium]
- **File:** SwipeSort/Core/WindowedThumbnailCache.swift:34
- **What:** `slide(to:total:)` is `async` but not isolated to any actor. `currentWindow` is read and written inside the function, and two rapid swipes can each call `slide()` concurrently — the second call reads the not-yet-updated `currentWindow` from the first call, producing overlapping start/stop sets.
- **Why it matters / failure scenario:** User swipes three photos in rapid succession. Three concurrent `slide()` calls are dispatched (from three `onChange(of: model.currentIndex)` Tasks). All three read `currentWindow = 0..<7` (the old window), compute overlapping `toStart`/`toStop` deltas against the same stale base, and issue redundant `startCachingThumbnails` and `stopCachingThumbnails` calls. According to RESEARCH.md §4.2, mismatched start/stop pairs cause `PHCachingImageManager` to leak memory.
- **Suggested fix direction:** Mark `WindowedThumbnailCache` as `@MainActor` (it already is) — check whether `slide()` is always called from a `MainActor` context. If `onChange` Tasks run off-main, add explicit `MainActor.run` wrappers around the `slide()` call. Since the class is already `@MainActor` the real risk is only if the `Task { await thumbnailCache?.slide(...) }` created in `onChange` ever hops off-main, which it should not for a `@MainActor`-isolated async function — but this should be verified.
- **Verified:** pending (likely safe given `@MainActor` on the class, but the Task wrapping in `SwipeStackView` does not explicitly enforce this)

### F16 — `swipePrev()` skips assets with pending decisions, but `undo()` walk does not align with this skip logic [SEVERITY: medium]
- **File:** SwipeSort/Features/Swipe/SwipeSessionModel.swift:127
- **What:** `swipePrev()` walks backward skipping assets that already have a decision in the queue (line 132: `!decidedIDs.contains(assetID)`). `undo()` walks backward looking for the identifier of the popped decision. After an undo + re-decision cycle, `findPrevIndex()` in `loadCurrent()` also skips decided assets. If the user does: swipe A (keep), swipe B (delete), press Undo (pops B), swipe C (next without deciding B), the decided set now contains {A}. `findPrevIndex()` from index of C looks back and finds B (undecided) — correct. But if the user then presses Undo again, `undo()` walks from `min(currentIndex, totalCount-1)` looking for C's identifier (the popped decision from the second undo call) — correct. The logic is consistent here. However, `swipePrev()` skipping decided assets means the user could press "prev" repeatedly and never land on an asset they already decided on, contradicting the "see the previous photo" UX expectation.
- **Why it matters / failure scenario:** User swipes 5 photos (all keep), then presses "prev". The backward walk skips all 5 decided photos and returns nil (guard fires, `swipePrev` no-ops), leaving the user unable to navigate back at all — even though they can see via the UI that there are previous photos (the header shows "6 of 50").
- **Suggested fix direction:** Re-evaluate the skip logic in `swipePrev()`. Either remove it entirely (let the user navigate back to already-decided photos without undoing), or make the skip optional based on a user preference. The skip logic was designed to mimic "undo" but should not block backward navigation.
- **Verified:** pending

### F17 — `PhotoKitLibrary.userAlbums()` enumerates `PHAsset.fetchAssets(in:)` for every album to get `assetCount`, making it O(albumCount × fetchCost) [SEVERITY: medium]
- **File:** SwipeSort/Core/PhotoKitLibrary.swift:175
- **What:** For each album in the `PHAssetCollection` enumeration, a separate `PHAsset.fetchAssets(in: col, options: nil)` is called to read `countFetch.count`. This is called from multiple sites (album list, `onChange(of: model.phase)` for every phase change to `.ready`).
- **Why it matters / failure scenario:** A library with 200 user albums calls `userAlbums()` on every navigation to `.ready` phase (once per swipe in `SwipeStackView.onChange`). Alternatively, cache the album list and refresh only on library change notifications.
