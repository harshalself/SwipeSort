# Performance & Memory
**Reviewer:** performance-lens  **Date:** 2026-07-13  **Verify status:** pass

## Summary
The codebase has a solid structural baseline: `WindowedThumbnailCache` uses delta-only start/stop caching, `VideoPlayerPool` caps hardware decoders at three, and `GridImageCache` provides a cost-aware `NSCache`. However, several real-world failure modes remain. The most dangerous is that `loadCurrent` pre-fetches thumbnails for current, next, and previous cards on the main actor in a way that can starve the UI during slow iCloud downloads, while four parallel `async let` continuations all await back on `@MainActor`. A library-change notification with no debounce will flood both grid views on every commit or system iCloud sync event. The `WindowedThumbnailCache` window (5 ahead, 2 behind = 8 assets) is undersized for a 50 k-asset library where a user can drag-jump ten cards at once, and `resolveIdentifiers` quietly over-fetches across a span that may include hundreds of skipped indices in a non-contiguous set. The grid `NSCache` is sized at 600 items × 80 MB, but on 3× iPhones at 400 × 400 px each cached image actually costs ~640 KB, so 600 items at peak = 384 MB before the OS cap fires — far above the 80 MB `totalCostLimit`. Two findings (F4, F7) are medium-severity quality issues; all others are high or critical.

## Findings

### F2 — Library-change notification triggers unbounced loadAssets in both RecentsView and AlbumsView [SEVERITY: high]
- **File:** SwipeSort/Features/Landing/RecentsView.swift:238–240 and SwipeSort/Features/Landing/AlbumsView.swift:98–100
- **What:** Both views subscribe to `PhotoLibraryChangePublisher.didChangeNotification` with a raw `onReceive` that immediately fires `loadAssets()` / `loadAlbums()` with no debounce or coalescing.
- **Why it matters / failure scenario:** During a swipe session that commits 200 deletions in a single `performChanges` block, `PHPhotoLibraryChangeObserver` fires once per batch — but during iCloud sync, the Photos daemon can dispatch dozens of change notifications in rapid succession (one per downloaded asset). Each notification causes both views to call `refreshFetchResult`, `applyFilter`, `assetCount`, and `identifiers(in:)` — a full re-index on the main actor. With a 50k-asset library, each re-index is a non-trivial Photos DB query. If the grid tabs are both in the responder tree simultaneously (the default tab setup), they both re-index concurrently, multiplying the load. This also churns `assetIds` causing the grid to fully invalidate and reload, dropping smooth scroll position.
- **Suggested fix direction:** Coalesce notifications with a short debounce (e.g. 0.5 s) before calling `loadAssets`. A `Task`-based debounce that cancels any pending reload task when a new notification arrives is sufficient. Alternatively, use `PHChange` delta objects in the change observer to apply incremental updates instead of full re-fetches.
- **Verified:** yes (adversarial subagent confirmed — RecentsView:238-240 and AlbumsView:98-100 both fire raw unbounced `Task { await loadAssets() }` per notification)

### F3 — WindowedThumbnailCache window (5+2=7 assets) is too narrow for drag-jump navigation in a 50k library [SEVERITY: high]
- **File:** SwipeSort/Core/WindowedThumbnailCache.swift:25–27
- **What:** The default window is `aheadOf: 5, behind: 2`, covering 8 assets; when the user swipes or the model jumps to a non-adjacent index (e.g. `initialAssetId` resolution, undo walk), `slide()` starts caching up to 8 new assets and stops caching the previously held window — but at index 40,000 in a 50k library, every `slide` call must resolve asset identifiers via `library.identifiers(in:)`, each of which hits the Photos database.
- **Why it matters / failure scenario:** A user browsing a 50k library with rapid successive swipes issues one `slide()` call per swipe. If the user flicks through 20 cards in 2 seconds, 20 sequential `slide()` calls queue up, each doing two `library.identifiers(in:)` round-trips and two `startCachingImages`/`stopCachingImages` calls. Because `slide()` is `async` and marked `@MainActor`, it serializes on the main actor. The cumulative DB query latency can exceed the swipe animation window, causing the windowed cache to lag behind the visible card.
- **Suggested fix direction:** Increase the default window size (e.g. 10 ahead, 5 behind) and batch consecutive `slide()` calls so only the last-settled index drives a cache update (debounce or coalesce rapid calls). Alternatively, use a hysteresis approach: only slide the window if the new index is outside the current window, avoiding spurious stop/start pairs for single-card advances that are already in-window.
- **Verified:** plausible — window semantics and per-slide DB call are real; main-actor "stall" claim is overstated (each `await` suspends the main actor rather than holding it), but the backlog concern holds. Severity kept at high.

### F4 — GridImageCache NSCache cost calculation uses unscaled point-size pixels, understating true memory by 1–9× on retina devices [SEVERITY: high]
- **File:** SwipeSort/Features/Landing/RecentsView.swift:28–30
- **What:** The `store(_:for:)` cost calculation uses `image.size.width * image.size.height` — which is `UIImage.size` in points (logical units) — not the pixel dimensions. On a 3× display, a 400×400-pixel image has `UIImage.size` of `133×133` points, yielding a cost of `133*133*4 ≈ 70 KB` when the actual memory footprint is `400*400*4 = 640 KB`. The `totalCostLimit` of 80 MB is therefore roughly 9× too permissive.
- **Why it matters / failure scenario:** With a 3× iPhone and 600 cached items each at 640 KB actual cost, the cache can hold up to `600 × 640 KB = 384 MB` before `countLimit` evicts, while `totalCostLimit` (80 MB / understated 70 KB ≈ 1,142 "cost units") believes it has already fired long before the OS receives memory pressure. The result is the cache grows well beyond the 80 MB design intent without evicting, contributing to high memory usage that triggers `didReceiveMemoryWarning`.
- **Suggested fix direction:** Replace `image.size.width/height` with `image.cgImage?.width/height` (which returns actual pixel dimensions) or multiply by `image.scale` before computing the cost. This makes `totalCostLimit` effective as a real byte guard.
- **Verified:** yes (adversarial subagent confirmed — `image.size` is in points; on 3× displays a 400×400px image reports 133×133 points, so cost is understated ~9×; effective cap is `countLimit=600`, worst case ~384 MB)

### F5 — VideoPlayerPool.drain() is only called on SwipeStackView.onDisappear; sheet dismissals that don't disappear the parent view leak retained AVPlayers [SEVERITY: high]
- **File:** SwipeSort/Features/Swipe/SwipeStackView.swift:102–105 and SwipeSort/Core/VideoPlayerPool.swift:67–73
- **What:** `VideoPlayerPool.shared.drain()` is called only in `SwipeStackView.onDisappear`. When the user opens a sheet (e.g., `DeletionQueueView`, `FullResViewer`) from within `SwipeStackView`, the parent view does not disappear — `onDisappear` does not fire — so the pool is never drained if the user dismisses the swipe session from inside the sheet without returning to the card stack first.
- **Why it matters / failure scenario:** If the user taps "Delete Now" in the finished-summary sheet (line 508), the system commit dialog appears modally. If the user confirms deletion and then the sheet auto-dismisses, the parent `SwipeStackView` is also dismissed by `dismiss()` (line 508 calls `commitResult = await model.commitDecisions()` but does not call `dismiss()`). However if the view hierarchy tears down via `fullScreenCover` dismissal, `onDisappear` fires. The critical gap is the `FullResViewer` sheet: a user can open the pinch-zoom view and then navigate the app away without closing it explicitly, keeping `SwipeStackView` backgrounded. In this state the `@State private var model` retains the `VideoPlayerPool` slots indefinitely across multiple navigation sessions since `VideoPlayerPool.shared` is a global singleton.
- **Suggested fix direction:** Also call `VideoPlayerPool.shared.drain()` from a session-end path that fires regardless of the dismissal route — for example, when `model.phase` transitions to `.finished` or when the `SwipeSessionModel` deinits. Alternatively, make the pool session-scoped (not a singleton) so it is freed with the view state.
- **Verified:** plausible — architectural gap is real (no drain path from model phase transition or deinit); severity mitigated by hard pool cap of 3 slots. Kept at high.

### F6 — RecentsView.loadAssets calls both refreshFetchResult and applyFilter unconditionally on every invocation, causing two full DB cursor invalidations per notification [SEVERITY: high]
- **File:** SwipeSort/Features/Landing/RecentsView.swift:244–254
- **What:** `loadAssets()` always calls `library.refreshFetchResult()` followed immediately by `library.applyFilter(filter)`. `applyFilter` already nullifies `fetchResult` when the filter changes (PhotoKitLibrary.swift:483), and `refreshFetchResult` unconditionally sets `fetchResult = nil` (PhotoKitLibrary.swift:473). When the filter has not changed, calling `refreshFetchResult` before `applyFilter` causes two cursor invalidations in rapid succession where one would suffice.
- **Why it matters / failure scenario:** On every library-change notification (no debounce — see F2), the sequence is: (1) `refreshFetchResult` → cursor nil, (2) `applyFilter` (filter unchanged) → enters the guard-`filter != activeFilter` check, does nothing further to cursor but evaluates the predicate comparison. Then `assetCount()` triggers `ensureFetchResult()` which re-runs the Photos DB query. While this doesn't cause data loss, with rapid notifications it causes double-invalidation cycles, and `applyFilter` with an equal filter still takes a function call + actor hop. On AlbumGridView, the same pattern exists: `s.refreshFetchResult()` then `s.applyFilter(filter)` at lines 319–320.
- **Suggested fix direction:** Remove the unconditional `refreshFetchResult()` call from `loadAssets`. Let `applyFilter` handle cursor invalidation when the filter changes. Add a separate signal (e.g. a `needsRefresh` flag toggled by the change notification) to force a re-fetch when the filter has not changed but the library contents have. This reduces the redundant invalidation to a single deliberate operation.
- **Verified:** yes (adversarial subagent confirmed — `refreshFetchResult` nil-s the cursor unconditionally, `applyFilter` guards on filter change; when filter is unchanged the cursor is needlessly nil-ed. Same pattern in AlbumGridView lines 319-320)

### F7 — SwipeStackView.task block does not have a cancellation path if the view disappears during library.applyFilter or model.start() [SEVERITY: medium]
- **File:** SwipeSort/Features/Swipe/SwipeStackView.swift:83–93
- **What:** The `.task { }` modifier on `SwipeStackView` (lines 83–93) calls `library.applyFilter`, `model.start()`, `library.userAlbums()`, and `thumbnailCache?.slide()` in a linear sequence with no `Task.isCancelled` checks and no structured cancellation checkpoints between the awaits.
- **Why it matters / failure scenario:** If the user immediately dismisses the swipe deck (taps `×`) while the task is mid-way through `model.start()` (which calls `library.assetCount()` and `library.identifiers(in:)` — both Photos DB round-trips), the `.task` modifier will cancel the Swift task but only at the next cooperative suspension point. `PhotoKit` callbacks are not cancellation-aware — once `requestImage` is in flight, it runs to completion. The main risk is a `userAlbums()` call that issues `PHAsset.fetchAssets` for every album (line 175 of `PhotoKitLibrary.swift`) on a library with hundreds of albums; this completes even after the view has gone, writing back to the `@State` albums array on a deallocated view. SwiftUI handles this safely for `@State`, but the album enumeration work (O(albums × assetCount queries)) is pure waste.
- **Suggested fix direction:** Add `try Task.checkCancellation()` between each major await inside the `.task` body to allow early exit. Also consider cancelling in-flight `PHImageRequest` calls by storing request IDs and calling `cancelImageRequest(_:)` on `onDisappear`.
- **Verified:** pending

### F8 — cardPixelSize is computed from hard-coded 400×600 points without calling PixelSize.from(points:) at runtime scale [SEVERITY: medium]
- **File:** SwipeSort/Features/Swipe/SwipeStackView.swift:47–48
- **What:** `cardPixelSize` is set with `PixelSize.from(points: CGSize(width: 400, height: 600))` in `init`, which calls `UITraitCollection.current.displayScale` at init time. SwipeStackView is constructed during a `State(initialValue:)` call inside `init`, which executes before the view is attached to a display — `UITraitCollection.current` may return scale `1.0` (the default) rather than the actual device scale.
- **Why it matters / failure scenario:** On a 3× device, if `UITraitCollection.current.displayScale` is `1.0` at init time, `cardPixelSize` becomes `CGSize(400, 600)` instead of `CGSize(1200, 1800)`. All swipe card thumbnails are requested at 400×600 pixels — displayed at ~1200×1800 physical pixels — producing blurry cards. The thumbnails are also cached by `WindowedThumbnailCache` at the wrong size, so even if a correct-size request is made later, the cache holds undersized images.
- **Suggested fix direction:** Move `cardPixelSize` computation out of `init` and into the `.task` or `onAppear` modifier where `UITraitCollection.current` reflects the actual display. Pass `targetSize` to `SwipeSessionModel` and `WindowedThumbnailCache` only after the view is on-screen. Alternatively, read the scale from `UIScreen.main.scale` which is available before view attachment (though deprecated in iOS 17+; the environment's `\.pixelLength` is the modern equivalent).
- **Verified:** pending

### F9 — WindowedThumbnailCache.resolveIdentifiers over-fetches a contiguous span that may include sparse non-adjacent indices after jumps [SEVERITY: medium]
- **File:** SwipeSort/Core/WindowedThumbnailCache.swift:80–92
- **What:** `resolveIdentifiers(at:)` fetches `library.identifiers(in: first..<(last+1))` — a contiguous range between the minimum and maximum requested indices — even when the `indices` array is sparse (e.g., `[0, 5, 10]` fetches indices 0–10, 11 items, to retrieve 3).
- **Why it matters / failure scenario:** When `slide()` is called after an `undo()` that walks back 20 cards, `toStop` and `toStart` sets can be non-contiguous spans of width 20+. `resolveIdentifiers` then fetches up to 20 identifiers from Photos DB to retrieve the 5–7 actually needed. In a 50k-asset library this is a minor overhead per call, but combined with F2 (unbounced notifications) and F3 (narrow window causing frequent re-slides), the cumulative Photos DB query pressure is meaningful.
- **Suggested fix direction:** For non-contiguous index sets, either batch into multiple small contiguous fetches or pass the `Set<Int>` directly to `library.identifiers(in:)` if the protocol is extended to accept an `IndexSet`. Alternatively, keep the current over-fetch but add a comment documenting that it is acceptable only for window sizes ≤ 20.
- **Verified:** pending

### F10 — GridImageCache.kinds dictionary is unbounded; with 50k assets it grows without any eviction policy [SEVERITY: medium]
- **File:** SwipeSort/Features/Landing/RecentsView.swift:21 and SwipeSort/Features/Landing/RecentsView.swift:35–39
- **What:** `GridImageCache` uses an `NSCache` for images (with count and cost limits) but stores `MediaKind` values in a plain `[String: MediaKind]` dictionary (`kinds`) with no size cap and no eviction.
- **Why it matters / failure scenario:** `RecentsView` loads up to 500 asset identifiers; `AlbumGridView` loads up to 1000. Each time a `ThumbnailCell` loads a new asset's media kind, it stores a `MediaKind` enum value (a Swift value type, ~40 bytes including associated values) keyed by the identifier string. With 1,000 entries that is trivial (~40 KB). However, `GridImageCache` lives in `@State` and is never reset between filter changes — after the user changes the filter several times, the dictionary accumulates stale entries from previous filter sets. Since `kinds` is keyed by raw `AssetIdentifier` strings that may not appear in the current filtered set, the entries are dead weight. Memory impact is small but the unbounded growth is architecturally inconsistent with the `NSCache` approach used for images.
- **Suggested fix direction:** Either apply the same `NSCache` approach to kind storage (wrap `MediaKind` in an `NSObject` subclass), or invalidate the `kinds` dictionary when the filter changes (hook into `loadAssets` or the filter change path). A simpler fix: cap the dictionary to the current `assetIds` set after each `loadAssets` call.
- **Verified:** pending

### F11 — thumbnailCache.stopAll() in onDisappear is not guarded against racing with a concurrent slide() task [SEVERITY: medium]
- **File:** SwipeSort/Features/Swipe/SwipeStackView.swift:102–105 and SwipeSort/Core/WindowedThumbnailCache.swift:71–74
- **What:** `onDisappear` calls `thumbnailCache?.stopAll()` synchronously, but `onChange(of: model.currentIndex)` spawns `Task { await thumbnailCache?.slide(...) }` that may be in-flight. `stopAll()` resets `currentWindow = 0..<0` and calls `stopCachingAllThumbnails()`. If a concurrent `slide()` task runs after `stopAll()` completes (because the Task was queued before disappear), it will call `startCachingImages` on assets that should no longer be cached, and update `currentWindow` to a non-empty range — leaving caching running after the view is gone.
- **Why it matters / failure scenario:** A rapid swipe just before navigating away queues a `slide()` Task. `onDisappear` fires synchronously, calls `stopAll()`, resets `currentWindow`. Milliseconds later the queued `slide()` resumes, computes a diff against the now-empty `currentWindow`, and starts caching the new window. The cache runs indefinitely until the next `stopAll()` call, which never comes since the view is gone.
- **Suggested fix direction:** Track the slide task in a stored `Task` property and cancel it in `onDisappear` before calling `stopAll()`. Since both are `@MainActor`, the cancel and the stopAll execute in the same actor turn, preventing the race.
- **Verified:** pending

### F12 — iCloud download progress is not surfaced to the user; thumbnail() silently returns nil on download failure with no retry [SEVERITY: medium]
- **File:** SwipeSort/Core/PhotoKitLibrary.swift:65–120
- **What:** `thumbnail(for:targetSize:)` sets `isNetworkAccessAllowed = true` but has no `progressHandler` on `PHImageRequestOptions`. When an iCloud-only asset begins downloading, `PHImageManager` will not call the result handler until the download completes or fails; if it fails (no network, timeout), the handler fires with `image == nil` and `PHImageErrorKey` set — the method returns `nil`. The caller (`ThumbnailCell`, `SwipeSessionModel.loadCurrent`) receives `nil` and shows a blank placeholder with no indication of why.
- **Why it matters / failure scenario:** A user with a large iCloud Photo Library on cellular with poor signal will see blank swipe cards for every undownloaded asset. There is no spinner, no "Downloading from iCloud" indicator, and no retry. The session model advances to the next card only after a swipe gesture — the user is stuck on a blank card until they manually swipe. Additionally, `PHVideoRequestOptions` in `avPlayerItem(for:)` also has no `progressHandler`, so video cards silently fail.
- **Suggested fix direction:** Add a `progressHandler` to `PHImageRequestOptions` that publishes download progress via a continuation or an `@Observable` property visible to the card view. Show a progress view on the card when `isDegraded == true` and `isNetworkAccessAllowed` is active. Implement a retry or automatic re-request on failure.
- **Verified:** pending

### F13 — AlbumGridView loads up to 1000 asset identifiers into memory while RecentsView caps at 500; neither uses pagination [SEVERITY: low]
- **File:** SwipeSort/Features/Landing/AlbumsView.swift:322–323 and SwipeSort/Features/Landing/RecentsView.swift:251–252
- **What:** Both views materialize a full array of `AssetIdentifier` values from `library.identifiers(in:)` — up to 1,000 for album grids and 500 for recents — into `@State var assetIds: [AssetIdentifier]`. With string-valued identifiers (~64 bytes each), 1,000 items is only ~64 KB — negligible. However, every `ForEach(Array(assetIds.enumerated()), ...)` in the grid re-enumerates the full array on each state change, and the `LazyVGrid` instantiates `ThumbnailCell` views lazily but keeps all `ForEach` nodes in the render tree.
- **Why it matters / failure scenario:** For an album with exactly 1,000 photos, the grid holds 1,000 `ForEach` identity entries. Each filter or selection state change triggers a full `ForEach` diff. This is unlikely to be perceptible but represents a floor of unnecessary work on every SwiftUI layout pass. It also means the hard cap of 1,000/500 is a silent truncation — users with larger albums will not see all their photos without any indication.
- **Suggested fix direction:** Implement cursor-based pagination: load an initial batch (e.g., 200) and append more as the user scrolls near the end. This reduces both memory and `ForEach` diff overhead, and removes the silent truncation. At minimum, show a message when the count exceeds the cap.
- **Verified:** pending

### F14 — VideoPlayerPool eviction replaces the player item with nil but does not cancel any pending AVAssetResourceLoading requests [SEVERITY: low]
- **File:** SwipeSort/Core/VideoPlayerPool.swift:46–51
- **What:** When evicting the LRU slot, the pool calls `evicted.player.replaceCurrentItem(with: nil)`. This removes the current item but does not call `cancelLoading()` on any in-flight `AVAssetResourceLoadingRequest` objects attached to a custom resource loader, nor does it ensure the underlying `AVURLAsset` is released.
- **Why it matters / failure scenario:** For standard `http(s)://` or local assets this is harmless — `AVFoundation` cancels loading internally on `replaceCurrentItem(with: nil)`. For iCloud assets delivered via `PHImageManager.requestPlayerItem`, the asset backing is a Photos-managed `AVAsset`; evicting the player does not cancel the Photos download request that was issued to produce the `AVPlayerItem`. The download continues in the background, consuming bandwidth and memory until it completes, even though no player will use the result.
- **Suggested fix direction:** When evicting, explicitly track and cancel the original `PHImageManager` request ID for the video item. Store the request ID alongside the `Slot` and call `imageManager.cancelImageRequest(_:)` on eviction.
- **Verified:** pending (medium-severity, not adversarially verified per the review protocol)

## Refuted (removed by verify pass)

### F1 — loadCurrent fires 4 async-let tasks that all resume on @MainActor, blocking the run loop during iCloud downloads
**Verdict:** refuted. `thumbnail(for:targetSize:)` and `mediaKind(for:)` in `PhotoLibraryProviding` are not `@MainActor` isolated, so `async let` launches child tasks on the cooperative thread pool. The `await` on line 308 suspends the `@MainActor` function and yields the main actor while PhotoKit work proceeds on background threads — the main actor is free to handle UI events during those awaits. The main-actor-stall claim is incorrect. The legitimate concern (iCloud latency delaying `currentThumbnail` assignment) is real but is not a main-actor stall and does not warrant high severity. Downgraded to low; removed from the ranked findings.
